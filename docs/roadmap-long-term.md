## 1. 现状诊断

### 1.1 能力盘点：功能广度已越过"够用"线

迭代 01–05 把 C# 前身 5 年积累的移植池**全部清空**，当前能力面：

| 域 | 状态 |
|---|---|
| Git 工作流 | 完备。含 bisect、操作级 undo（reflog）、worktree 一等公民、交互式 rebase、cherry-pick |
| Diff / Merge | 行/hunk/文件三级暂存、三方合并编辑器（zdiff3 + autosolve + 手动对齐）、内联编辑、图片 diff |
| 平台联动 | GitHub PR 列表 + CI chip + checkout PR ref、GitLab push options、双 forge 建 PR/MR 网页闭环 |
| AI | commit message / hunk 解释 / MR 描述，7 类 provider 矩阵，凭证本地按需解析 |
| Agent 工作台 | v2：专用 worktree 隔离、基线 diff、路径级接受/拒绝、会话列表面板 |
| 桌面体验 | 覆盖率 overlay、贡献统计、多标签会话恢复、明暗主题、i18n（en/zh-CN）、命令面板、内嵌终端 |
| 大仓库 | 增量 status（事件驱动 + 路径定向）、mimalloc、rust-lld、perf 预算 CI |

**结论**：功能清单层面已进入**边际递减区**——再补单项功能不再改变用户选型。

### 1.2 结构盘点：重构接近收尾，但用户感知为零

- 规模：860 个 `.rs` / **59.5 万行**；`worktree-ui-gpui` 独占 **40.9 万行（69%）**
- 重构进度：P0–P4 已合入 dev 并推平（`GitRepository` 176 方法 → 七域 trait、167 个 `_impl` 委托壳宏化、`run_git` 36→1、session persist 10 对收敛、`reduce_inner` 262 臂分派化）；**P5「split remaining」进行中**（分支 45 提交，dev 已合 2 件）
- 代码卫生极好：`TODO/FIXME/HACK` grep **零命中**、`dead_code` 约 22 处、`unsafe` 仅存在于 `win32-window-utils`
- 残余：>2,000 行文件 73 个（含测试文件），P5 目标收口至 <10

### 1.3 性能盘点：测量基建已齐备，卡在"门控未通 + 数字未出仓"

> **勘误（2026-09-14 二次实测）**：初稿判断"没有可公开复现的基准"，实测后证伪——测量基建比预想完整得多。修正如下。

README 的第一句话是「The fastest open-source Git GUI」「在 Chromium 规模仓库上保持流畅是每条功能的门槛」。支撑它的基建**已经存在**：

- **预算框架**：`worktree-ui-gpui/src/bin/perf_budget_report`（structural 7 域 + timing 4 域，逐条 `PerfBudgetSpec` 带阈值与注释）
- **合成仓库档位**：`open_repo/{balanced,history_heavy,branch_heavy,extreme_metadata_fanout}`、`history_cache_build/50k_commits_2k_refs_200_stashes`、`branch_sidebar/20k_branches_100_remotes`、`repo_switch/20_repos_all_hot`
- **真实仓库接入点**：`WORKTREE_PERF_REAL_REPO_ROOT`（`benches/performance/real_repo.rs`），CI 变量 `PERF_REAL_REPO_ROOT` 驱动
- **专项 harness**：`perf-app-launch`（cold/warm × 1/5/20 repos）、`perf_idle_resource`（CPU、内存增长、后台刷新成本、睡眠唤醒）
- **工具链**：`scripts/{run-full-perf-suite,compare-perf-runs,archive-perf-run}.sh`
- **最新两个提交已转向性能**：on-disk ref-fingerprint history cache（`history_cache.rs` 437→805 行）+ 有界快照分页 + refs 单次枚举

**真正的缺口是三处，且都不是"建基准"**：

1. **strict 门控实际可能从未生效**：`perf.yml` 的 strict 分支要求 CI 变量 `PERF_RUNNER` 与 `PERF_REAL_REPO_ROOT` **都已配置**；否则静默 fallback 到共享 runner 的 alerting 模式（`--skip-missing`，且 job 带 `continue-on-error: true`）。即"有 strict 但可能没开门"。
2. **数字没有出仓**：README 无实测表，外部无法引用；`compare-perf-runs.sh` 的产物没有对外发布路径。
3. **冷启动有测量、无优化**：`app_launch/cold_*` 已在测，但 C# 版那套四连优化（跳过冷启动探测、重活离 UI 线程、恢复 tab 不实例化全部仓库）**尚未移植**。

### 1.4 工程与产品化盘点

- CI：12 个 workflow（rust / cross-platform-tests 含 windows-arm64 / benchmark-targets / perf / 6 个 deploy / release-manual-main）
- 分发：GitHub Releases、MS Store、Homebrew cask、AUR、GURU、apt 仓库 —— **渠道已经很全**
- 缺口：无 CHANGELOG / 用户可见版本说明；`Cargo.toml` 版本 **0.3.0** 与 roadmap 内部迭代号 v0.6.0 **脱节**，对外沟通存在歧义

### 1.5 2026-09-14 核查：发现两个上游阻塞（优先于本方案任何迭代）

实施方案时做 T0 核查，发现两个比"排哪个迭代"更根本的问题：

**① CI 已停摆 19 天。** 8-27 至今全部 workflow 运行数为 **0**；最后一次运行（8-26）Clippy `exit 101` + Rustfmt `exit 1` 失败，测试各腿全绿。期间远端 dev 有几十个提交。**性能门控、质量收口的一切前提都不成立**——已在迭代 06 规格中提升为 P0。

**② 仓库仍是 `private`。** 0 stars、0 open issues，而 README 在引导 star / Releases / Discord、LICENSE 为 AGPL-3.0。

> **决策（2026-09-14 用户拍板）：保持私有，尚未到开源时机。** 影响如下：
>
> - **迭代 08「扩展生态」的立项理由要改写**：插件生态的价值主要来自第三方贡献者，私有阶段没有这个前提。扩展系统降级为**自用取向**——脚本命令与钩子对单人/小团队仍有价值（可自动化重复操作），但不再以"生态"为目标，优先级下调，与"配置档案""PR review"等团队项同层。
> - **决策点 D10（商业模式）暂缓**，待开源时机再议。
> - **迭代 06「性能可证明」不受影响**：性能是内部质量标准，与是否开源无关，**继续作为下一站**。
> - **迭代 09 新增一项「开源前准备清单」**：README 对外文案与私有现状的一致性核对、LICENSE/NOTICE 复核、6 个分发渠道（含 MS Store）的合规检查、Discord 与 worktree.dev 是否启用。**这些事在决定开源前不必做，但清单要先有**，避免临时抱佛脚。

> 附带：perf.yml 只有 `schedule` + `workflow_dispatch` 触发，**没有 `pull_request` 触发器**——PR 性能门控在设计上就不存在，原方案"双层拆分"的口径应改为"新增 PR 触发器"。

## 2. 三个战略判断

**判断 1 · 护城河必须从"广度"换到"深度"。**
功能清单是抄得动的。抄不动的是：超大仓库的**实测性能**、agent 时代的工作流形态、以及本地优先的可信度。

**判断 2 · AI 已从加分项变成主战场形态。**
2026 年 Git GUI 的关键分野是：能否**安全承接 agent 产出的改动**。WorkTree 的 agent 工作台（隔离 worktree + 基线 diff + 路径级接受/拒绝）是这个位置上少有的正确设计，但 v1/v2 只做到"能跑"，离"每天主力用"还差并行、持久化、时间线、聚合视图四块。

**判断 3 · P5 之后应设"结构冻结期"。**
重构收益是结构性的，用户感知为零。P5 收口后建议冻结结构专项 2–3 个迭代，产能全部投向用户可感知的改进——否则会陷入无限清理。

## 3. 长期路线（迭代 06 – 09）

工作量 S/M/L 按单人周粗估，沿用既有口径。

### 迭代 06 — v0.7.0「性能可证明」（4–6 周）★ 建议下一站

**目标**：把「最快」从口号变成有公开数字、有 CI 守护的护城河。

1. **打通 strict 门控 + 数字出仓** `M`（**不是新建基准，是让已有基建生效**）
   - **P0 前置核查**：确认 CI 变量 `PERF_RUNNER` / `PERF_REAL_REPO_ROOT` 是否已配置。若未配置，strict 门控从未真正运行过——这是本迭代**第一个动作**，且结论可能直接改写后续排期。
   - 为真实仓库档位固定"靶子快照"（一个公开超大仓库的稳定快照 + 版本化 manifest），消除"每次测的不是同一个仓库"的可比性问题。
   - 把 `perf.yml` 从"单一 `continue-on-error` job"拆成两层：PR 触发的轻量子集（门控）+ 周调度全量（告警），避免 PR 被 120 分钟全量阻塞。
   - 输出：README 实测表（档位 × 操作矩阵）+ 每个 release 一份 `compare-perf-runs` 对比。
2. **冷启动专项** `M`
   移植 C# 版四连优化：跳过冷启动探测、重活离 UI 线程、恢复 tab 不实例化全部仓库。目标值**先由 `perf-app-launch` 测出现状基线再定**，不预设数字。
3. **history cache 纵深** `M`
   刚落地的 ref-fingerprint 磁盘缓存从 log 扩展到 blame / reflog / 提交搜索；补缓存失效策略（ref 指纹 + LRU + 磁盘上限 + 手动清理入口）。
4. **大文件 / 大 diff 专项** `M`
   >10MB 单文件与 >5 万行 diff 的虚拟化与增量解码策略。现状是继"全量 status"之后最主要的卡顿源（status 已由增量 status 解决）。
5. **增量 status 收尾** `S`
   `.git/index` 事件走 index-lane 定向；watcher pathspec 对齐大小写不敏感文件系统（macOS 默认）的路径形态。

### 迭代 07 — v0.8.0「agent 工作台主力化」（6–8 周）

**目标**：让 agent 会话从"演示功能"变成"日常主力"。

1. **每 repo 多会话并行** `M`：数据模型从每 repo 单会话改为会话集合（v2 明确顺延项）。
2. **会话持久化与可回放** `M`：会话元数据落盘（baseline、worktree 路径、时间、结束状态、关联 repo），重启后可续；会话历史面板。
3. **自动快照节奏** `S`：按需查看 → 定时/事件触发快照，形成"改动时间线"，可回看任意时点。
4. **跨会话聚合视图** `M`：一次看清多个 agent 会话的全部改动，批量接受/拒绝。
5. **与 PR 描述生成打通** `S`：agent 会话改动 → 一键生成 PR/MR 描述（复用迭代 04-3 的生成器）。
6. **agent 安全边界** `S`：会话内高风险命令的审批提示；坚持本地优先——不上传任何内容。

### 迭代 08 — v0.9.0「扩展生态 + 团队场景」（6–8 周）

**目标**：从"个人工具"走向"可被定制、可被团队采纳"。

1. **扩展系统 v1** `L`（重启迭代 04-1 搁置项；**仓库保持私有，立项理由改写**）
   声明式优先：外置配置注册命令面板条目 + 脚本命令 + `RepositoryOpened`/`BeforeCommit`/`AfterCommit` 钩子。进程内 / WASM 留二期（Rust ABI 不稳定，不早投）。
   **定位调整**：不再以"第三方生态"为目标，改为**自用取向**——价值是自动化本人/本团队的重复操作。因此优先级与 08-3/08-4 同层，不再独占本迭代主线；若排期紧张可顺延至迭代 09。
2. **PAT 与自托管 host** `S`：手动 PAT 设置字段、GitHub Enterprise / 自托管 GitLab host 配置（03-6 + 05-3 顺延）。
3. **PR review 轻闭环** `M`：PR diff 本地打开、评论只读展示、check-runs 汇总 API（合并 03-6 顺延项）。
4. **配置档案（profile）** `M`：仓库级 user/email/gpgsign 已有（迭代 05 追加项）→ 抽象为可切换的身份档案，服务多身份场景（公司/开源）。
5. **可发现性** `S`：内置快捷键速查面板、文档站与 CLI help 补齐。

### 迭代 09 — v1.0.0「产品化收口」（4–6 周）

**目标**：为 1.0 收敛质量标准与发布纪律。

1. **版本与发布纪律** `S`：CHANGELOG、语义化版本、对外版本号与内部迭代号对齐（当前 0.3.0 vs v0.6.0）。
2. **崩溃与稳定性治理** `M`：崩溃/ANR 分类看板；本地 opt-in 遥测 vs 纯本地日志聚合，取决于 D7。
3. **质量收口** `M`：`diff_view.rs` 测试分期收尾（05-5 开了头）、i18n key 覆盖脚本进 CI、flaky 注册表清零。
4. **无障碍与输入** `M`：键盘全链路可达性回归（新功能持续侵蚀）、高对比度主题、屏幕阅读器标签。
5. **配置迁移与兼容** `S`：配置文件 schema 版本化 + 迁移路径（1.0 的长周期承诺）。

## 6. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| P5 未收口即开启功能迭代，结构债回潮 | 中 | P5 后设结构冻结期；新功能伴生的小结构整理就地做，不立专项 |
| 性能基准在共享 CI runner 上噪声大（perf.yml 已注明） | 高（基准不可信则整套承诺失效） | 门控只跑 PR 轻量子集 + 容忍带；对外数字以固定自持 runner 为准 |
| agent 生态剧变（CLI/协议变更）导致工作台返工 | 中 | 保持"进程级调用 + 通用 HTTP"的松耦合，不绑定单一 agent 内部 API |
| AI provider 凭证解析依赖第三方文件（claude/codex/gh）格式 | 中 | 已有 resolver 链；为每类解析补"格式变更即降级提示"而非静默失败 |
| 单人节奏下 06–09 共 20–28 周，跨度长 | 高 | 每个迭代独立可发布；顺延池每季度重排一次，允许换序 |
